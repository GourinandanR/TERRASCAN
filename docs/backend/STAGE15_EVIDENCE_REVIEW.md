# Stage 15 — Scientific Evidence Review & Quality Control

## Purpose
Stage 15 adds a human decision gate for source manifests and scientific observations. Review decisions are recorded with reviewer identity, a required rationale, timestamp, and audit event. Rejected records remain stored and visible in review history.

## Workflow
1. Register a dataset manifest. Its default status is `pending-human-review`.
2. Review the source product's official label, identity, checksum, source URL, CRS/datum, units, scale/offset, footprint, temporal coverage, quality and uncertainty.
3. Submit a manifest decision:
   ```http
   POST /api/manifests/{id}/review
   Content-Type: application/json
   ```
   ```json
   {
     "decision": "approved",
     "reason": "Official product label, checksum and metadata reviewed.",
     "reviewer": "reviewer-id"
   }
   ```
   `decision` is `approved` or `rejected`; reason must contain at least 10 characters.
4. Observations can only be registered against an approved source manifest. New observations are themselves `pending-human-review`.
5. Review each observation against the source data and processing method:
   ```http
   POST /api/observations/{id}/review
   ```
   Use the same JSON body. An observation can be approved only when its source manifest is approved.
6. Comparison-run snapshots include only approved observations. The API still does not calculate similarity scores.

## API endpoints
- `GET /api/review-queue` — pending manifests and observations.
- `POST /api/manifests/{id}/review` — approve/reject source manifest.
- `POST /api/observations/{id}/review` — approve/reject observation.
- `GET /api/review-history` — append-only review decision history.
- `GET /api/audit` — system audit trail.

Repeated review decisions are rejected with HTTP 409. Create a corrected/new version rather than silently rewriting a reviewed record. A manifest created with explicit `review_status="approved"` remains supported for controlled imports and tests; production use should use the review endpoint and preserve the reviewer trail.

## Database migration
On startup, the backend adds nullable review metadata columns to existing observations if absent and creates the `review_events` table. Existing observations default to `pending-human-review`; no historical record is automatically promoted.

## Frontend
The Evidence Review workspace shows pending manifests and observations, requires reviewer identification and a reason, and provides approve/reject actions. The workspace requires the Stage 12 FastAPI service to be running.

## Validation
Install test dependencies and run from `backend/`:
```bash
pip install -r requirements-dev.txt
python -m pytest -q tests/test_api.py
```
Tests cover review gates, reviewer reasons, rejection persistence, repeated-decision protection, queue/history endpoints, and comparison snapshot filtering.

## Scientific limitations
Approval is a workflow decision, not a guarantee of scientific correctness. Human reviewers remain responsible for the source product interpretation, planetary reference frame, units, temporal comparability, uncertainty, and processing choices. No evidence is seeded and no similarity or mission-suitability scores are generated by this stage.
